Distribution for AI coding standards

AI coding standards,
shipped like a dependency.

Rules, agents, skills and guardrails as versioned npm packs — integrity-checked and signature-verified on install, routed to the right engineer and the right stack version. Written into native config for seven AI coding tools.

Try it in 5 minutes

One existing project. Four commands, nothing to write.

~/my-app — any repo with a package.json
  1. $npx bluetemberg init --non-interactive --profile frontend --platforms claude,cursor --omit-github Detects your stacks and writes bluetemberg.config.json plus llm/packages.json: the packs the profile preselects, with semver ranges. Pick the profile closest to your role — backend, fullstack, devops…
  2. $npx bluetemberg install Downloads each pack and refuses it unless its SHA-512 and npm registry signature check out. Pins exact versions in llm/packages-lock.json.
  3. $npx bluetemberg sync Writes .claude/ and .cursor/ in each tool's own format — only the rules whose stack range matches the versions in your lockfile.
  4. $npx bluetemberg detect Shows the stacks and versions it found and whether guidance covers them. Ask about any rule with npx bluetemberg why <rule>.

Commit the generated files; run npx bluetemberg sync --check in CI to catch drift. Remove it all with npx bluetemberg uninstall. Walked through on 0.19.0 with a Next.js 15 app.  Full walkthrough →

How it works

Standards install like dependencies. Every tool reads them natively.

01 / CHOOSE Pick a profile A profile preselects the packs for a role. Stack-specific packs are preselected only when their stack is in the project.
02 / INSTALL Verified on arrival Packs come from npm with semver ranges and a lockfile. install checks SHA-512, registry signatures and content before anything lands.
03 / SYNC Native in every tool sync writes each tool's own format and paths, version-gated per stack. sync --check fails CI on drift. Teammates can also get a zero-setup plugin.

Version-aware routing

Two axes, not one. Role decides who gets a rule. Stack decides which version of it.

  • By role Profiles match content to an engineer's work — frontend, backend, infra, design. Each teammate gets the standards that apply to them, and none that don't.
  • By stack & version Tag a rule with a version range; sync delivers it only where it's correct — resolving each stack's version from your config, lockfile, and dependencies. A Payload 2 rule never reaches a Payload 3 repo.
  • Queryable detect reports the stacks and versions it found; coverage checks whether version-correct guidance exists; why explains why a rule is in or out, and why --diff shows what a stack upgrade would change. All have --json twins, and bluetemberg mcp serve exposes them to any agent over MCP. Read-only — it answers, it never writes.

Humans + agents

Your team writes the standards. So can their agents.

  • Humans author Rules, agents, and skills are plain Markdown in llm/ — owned by the team, reviewed in PRs, versioned with your code. Run the wizard, pick a profile, done.
  • Agents operate Every command has a headless twin. init --non-interactive skips the wizard, sync --check fails CI on drift, and --help --json exposes the whole catalog. No keyboard required.
  • Agents author too The create-rule, create-skill and create-pack skills teach an agent the format. From 0.20.0, bluetemberg draft opens a draft for a stack gap and checks its frontmatter, range and cited sources. Only a human at a terminal can promote it.

Supply chain

Packs are dependencies. So they're verified like dependencies.

  • Registry signatures Packs from the npm registry have their ECDSA registry signature verified on every install — and re-checked any time with bluetemberg verify. Tampered or unsigned packages are refused — the same cryptographic provenance check npm itself runs.
  • SHA-512 integrity Every pack is hashed and checked against npm registry metadata. Install is refused if the hash is missing or doesn't match.
  • Registry host pinning Tarballs must download from the same host as the registry. A compromised registry response can't redirect a download to an attacker's host.
  • Safe extraction Tarballs are capped at 50 MB compressed and 100 MB extracted, and every entry is filtered for .. segments, symlinks and hardlinks. Nothing can fill your disk or write outside the pack's own directory.
  • Content scan Before a pack lands, its content is scanned for leaked credentials, secret exfiltration (HTTP, DNS, gh, git push, markdown beacons), hidden Unicode and instructions to disable hooks — and re-scanned when the scanner gains rules. From 0.20.0 external sources get the same scan. A blocking finding stops the install; softer patterns print a warning.
  • Capability report From 0.20.0, add, install and update list what a pack can make your tools do — guardrails, hook configs, the scripts a skill ships — and an update shows what it adds, changes or removes. You review behaviour, not just prose.
  • Enforced guardrails Rules are advice an assistant can skip. A guardrail compiles to a hook the tool runs before the call, so a violating command is blocked. A condition it cannot evaluate or a payload it cannot read blocks too — guardrails fail closed.
  • Lockfile Exact versions, resolved URLs, and integrity hashes pinned in llm/packages-lock.json. Every install resolves to the same bytes — the same model npm uses for package-lock.json.

Standards with receipts

Most AI rules are a model's best guess. Ours are checked against the source.

  • Primary sources Every claim past plain convention is verified against official docs, IETF RFCs, and vendor advisories — PostgreSQL, RFC 9110, OWASP, CISA. Sourced from the spec, not forum folklore.
  • Default-refute An independent agent tries to disprove each claim; only the ones that survive a majority of checks ship. Overstated guidance gets downgraded, not waved through.
  • Public receipts Every verdict and source is on the Research page — confirmed, or flagged "nuanced" and reworded. Including the claims we walked back.
